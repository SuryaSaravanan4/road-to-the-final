# Prompt for Fable 5 (Claude Code) — Phased roadmap: screenshot bracket ingestion, picks/leaderboard, virtual prediction markets

Copy everything below into Claude Code with Fable 5 selected, run from the root of this repo.

---

## Product vision

Road to the Final lets any fan track their team's path through any tournament — official or informal — including competitions that only exist as a photo of a bracket on someone's phone. The screenshot ingestion pipeline is the defensible moat. The prediction market is a Phase 3 retention mechanic, not the lead feature. This roadmap is ordered accordingly: ship and validate the core tracker first, then a lightweight engagement layer, and only build the full market if the engagement layer proves people want it.

## 0. Read the codebase first — don't write code yet

This is `road-to-the-final`: Next.js 16 / React 19 / TypeScript, Prisma + SQLite, Tailwind v4, Vitest, deployed to Vercel. Read `README.md`, then these files in order:

- `src/types/domain.ts` — shared domain types (`Standing`, `Fixture`, `BracketNode`, `ScenarioInput`, `RankedScenario`, `RoundPath`)
- `src/providers/SportsProvider.ts`, `src/providers/registry.ts`, `src/providers/football-data-org/` — the provider abstraction and its reference implementation
- `src/lib/cache.ts` — the TTL cache: note the in-flight request de-dupe (`inFlight` map) and the stale-fallback-on-fetch-failure behavior. This is deliberately an *optimization layer*, not a source of truth, and it degrades gracefully (see below, this matters for what you must NOT build the same way).
- `src/lib/db.ts` — note the Vercel `/tmp` workaround: on Vercel, `DATABASE_URL` is redirected to `/tmp`, which is **not persisted between cold starts and not shared across instances.** `cache.ts` tolerates this because losing a cache entry just means one extra upstream fetch. **A wallet balance, an open order, or a settled trade must never be allowed to live only in that same throwaway SQLite file** — flag this explicitly in your Phase 3 plan (see Phase 3, below). It doesn't block Phase 1 or Phase 2 (no money-like data exists yet), but it must be solved or clearly documented before Phase 3 persists anything wallet- or order-shaped.
- `src/reasoning/scenarioSchema.ts`, `src/reasoning/buildScenarioPrompt.ts`, `src/reasoning/claude-client.ts` — the reasoning layer: Zod-validated, tool-call-structured output (`submit_scenarios`), given only already-fetched real data. Never invents facts.
- `src/lib/scenario-ranking.ts` — pure, unit-tested, deterministic sort. Ranking is code, never model output.
- `src/lib/road-to-final.ts` — the orchestration: this is the most important file to understand. Pay attention to `KNOCKOUT_STAGE_ORDER`, how a confirmed loss (`winnerTeamId !== teamId`) ends the road early, and how a stage with a *confirmed* opponent (`scheduledInStage`) short-circuits the Claude reasoning call entirely (100% likelihood, no LLM needed) versus a stage where the opponent is still unknown (LLM reasoning call). Any scoring, settlement, or resolution logic you add in any phase has to respect this same distinction between "confirmed by data" and "reasoned by Claude."
- `src/app/api/path/route.ts`, `src/app/api/refresh/route.ts`, `src/app/api/cron/route.ts`, `src/hooks/useTournamentPath.ts`, `src/app/path/page.tsx` — request/refresh flow
- `src/components/*` and `src/app/globals.css` — the design system: CSS variables `--ink`, `--floodlight`, `--turf`, `--live-red`, `--chalk`; the split-flap scoreboard component (`SplitFlap.tsx` + the `.flap-*` CSS) is the one deliberately-animated element in an otherwise still UI. It is reserved for Phase 3 (see there) — don't spend it early.
- `prisma/schema.prisma` — currently just `CacheEntry`
- `tests/` — existing Vitest conventions

**The non-negotiable architectural rule, unchanged across all three phases:** ground truth is never generated by an LLM. Claude is only ever a reasoning or extraction layer whose output is schema-validated. Ordering, odds pricing, matching, and settlement are always deterministic, unit-tested code — never a model call.

## Phase 1 — Core Tracker (ship and validate first)

This is the unique, defensible core of the product. Everything else waits until this has real users. Scope for this phase:

**Provider abstraction.** Preserve and harden the existing `SportsProvider` interface (`src/providers/SportsProvider.ts`) and registry pattern (`src/providers/registry.ts`) — every new data source, official or informal, must implement this interface so caching, reasoning, and ranking need zero changes to support it.

**Claude reasoning layer for unknown opponents.** This already exists (`src/reasoning/*`, wired through `road-to-final.ts`) — for this phase, review it for correctness and robustness rather than rebuilding it: confirm it's exercised correctly for both official-provider data and (new, this phase) screenshot-ingested data, and that its Zod-validated, tool-call-structured output contract (`scenarioSchema.ts`) is respected everywhere it's called from.

**Path visualization.** The existing `/path` page, `RoundSection`, `ScenarioCard`, `DifficultyBadge`, `HomeSummary`, and the split-flap-adjacent visual language should work identically for screenshot-ingested competitions as they do for `football-data-org` ones — no fork in the UI layer per data source.

**Screenshot ingestion for underground/unlisted competitions.** Official APIs don't cover informal competitions (e.g. something like "DDN Legends") that only publish a bracket or schedule as an image. Bring those into the same pipeline:

- **New provider**, e.g. `ScreenshotBracketProvider`, implementing `SportsProvider.ts` exactly, so caching, reasoning, and ranking need zero changes to support it.
- **Extraction**: Claude vision reads an uploaded screenshot and returns schema-validated (Zod) structured data — rounds, matchups, team names, dates, and any results already visible in the image — following the same tool-call pattern as `scenarioSchema.ts`/`buildScenarioPrompt.ts`. Never free-text parsing.
- **Support more than single-elimination**: also handle double-elimination (winners/losers bracket), round-robin/group tables, and hybrid group-stage-then-knockout formats. Detect which shape it's looking at, or ask the user to specify if it's ambiguous.
- **Bracket shape is not the same axis as scoring system — don't conflate them.** Format (single-elim, double-elim, round-robin, hybrid) describes who plays whom. A separate axis describes how standing/advancement is determined, and not every competition uses win/loss elimination: some (informal ladders, many gaming/esports scenes) are rating-based — ELO or a similar continuous score that goes up/down per result rather than a fixed bracket position — with no discrete "eliminated" state at all. **Don't build rating-based scoring in Phase 1**, but design `Competition`'s schema so this isn't a breaking migration later: avoid hardcoding the assumption that every competition has a `format` enum value implying a bracket shape, and keep `Standing`-like data generic enough that a future `ratingSystem: "ELO" | null` (or similar) could sit alongside `format` rather than replacing it. Flag in your plan how you'd extend the schema for this later, but do not implement it now.
- **Per-field confidence + human confirmation is mandatory, not optional.** Since there's no upstream API to cross-check this data against, extracted fields with low confidence should be visually flagged in an editable preview, and *nothing* — not a `RoundPath`, not (later, Phase 2/3) a pick or a tradable market — gets created from this data until the user has confirmed or corrected it. A bad OCR read of a team name must never silently become ground truth.
- **Store the source image + raw extraction + user corrections together**, not just the final corrected bracket — this is what lets you debug bad extractions later and is generally good practice for any AI-extracted-then-human-corrected data pipeline.
- **Support re-ingestion**: a later screenshot (next round's bracket, or updated results) should update the existing stored bracket, not force creating a duplicate competition.
- Once confirmed, this bracket is ground truth exactly like football-data.org's — the reasoning layer and ranking run on top of it completely unmodified.
- Let a user choose their tracked competition from official provider(s) or any of their own screenshot-ingested ones.

**Testing & ADR conventions for this phase:**
- Keep `npm test` passing throughout; add tests as you go.
- Bracket extraction schema: reject malformed/incomplete model output the same way `scenarioSchema.ts` would.
- Cover the new provider's stage/round handling with the same rigor as `road-to-final.ts`'s existing tests.
- Write a short ADR (`docs/adr/` or similar) recording which bracket formats you support, how format detection works, and how confidence flagging is implemented, so the reasoning is preserved in the repo, not just in chat history.

**Phase 1 open design questions — answer in your plan or ask me:**
1. How should format detection work when a screenshot is ambiguous between, say, a small round-robin table and a knockout bracket — auto-detect with a confidence threshold that falls back to asking the user, or always ask the user to pick the format first?
2. What happens to a confirmed bracket if a re-ingested screenshot contradicts earlier user-confirmed data (not just adds to it) — does the user get shown a diff to approve, or does re-ingestion only ever add, never overwrite?

## Phase 2 — Engagement Layer (validate demand before complexity)

Do not start this phase until Phase 1 is shipped and I've confirmed it's validated with real users. Replace the full Kalshi-style prediction market with a lightweight picks-and-leaderboard system: users predict match outcomes, earn points, compete on a leaderboard. No order books. No matching engine. No wallets. No regulatory exposure. This proves whether users want to "trade" on outcomes or just want to feel invested in the bracket.

All existing architectural rules still apply here: **picks are scored by deterministic code, never model output.** A pick is correct or incorrect based only on real fixture resolution data (`Fixture.status === "FINISHED"` and `winnerTeamId`), the same signal `road-to-final.ts` already uses — Claude is never asked whether a pick was right.

**Scope:**
- Users submit a pick per fixture or per scenario (e.g. "I think Team X advances this round") before it's resolved.
- When the underlying fixture resolves via the existing refresh/cron flow (`/api/refresh`, `/api/cron`) — not a new polling system — deterministic code scores the pick and awards points.
- A leaderboard ranks users by total points, scoped however makes sense (per competition, all-time, or both — resolve in your plan).
- No virtual or real currency, no order book, no wallets, no matching engine — this phase is intentionally simple.

**New Prisma models** (name however fits your conventions):
- `User` (can be minimal for this phase — expand later in Phase 3 rather than over-building now)
- `Pick` (user, fixture/scenario reference, predicted outcome, submitted-at, resolved/correct status)
- Whatever aggregate or view supports the leaderboard (a computed query is fine; don't over-engineer a separate points-ledger table unless you have a specific reason to)

**Testing & ADR conventions for this phase:**
- Keep `npm test` passing; add tests for pick scoring against each real fixture outcome (win/loss/draw where applicable) and against void-like edge cases (postponed/cancelled fixtures — a pick on a fixture that never resolves should not silently count as wrong).
- Write a short ADR recording your scoring scheme and leaderboard scope decisions.

**Phase 2 open design questions — answer in your plan or ask me:**
1. Scoring scheme — flat points per correct pick, or weighted by the scenario's Claude-assessed difficulty/likelihood (careful: if weighted by likelihood, make sure the weighting is applied by deterministic code using the already-computed number, not re-judged by Claude)?
2. Can a user change a pick before the fixture starts, or is it locked at submission?
3. Do picks make sense at the scenario level (predicting an opponent that isn't confirmed yet) as well as the confirmed-fixture level, or only once a matchup is locked in?
4. Leaderboard scope and reset cadence — per-tournament only, global all-time, or both?

## Phase 3 — Virtual Prediction Markets (only if Phase 2 validates demand)

The full Kalshi-style market layer, built on top of the tournament path (and, if still in use, the Phase 2 picks data can coexist — resolve in your plan whether Phase 2 and Phase 3 run side by side or Phase 3 supersedes Phase 2). Virtual currency, not real money.

**Regulatory note — read before scoping this phase:** "virtual currency only" is not automatically safe from a regulatory standpoint for sports outcome markets. Rules vary by jurisdiction and can turn on factors beyond whether currency is redeemable for cash (e.g. whether it can be transferred, whether it confers any prize of value, how it's marketed). Legal review is recommended before shipping Phase 3 to real users — flag this to me explicitly in your Phase 3 plan rather than treating "virtual currency" as a self-evident safe harbor.

**Order book & matching**
- Limit orders only (no market orders for v1) on a 1–99¢ price grid, same as Kalshi (price = implied probability).
- Price-time priority matching: best price first, FIFO within a price level. Support partial fills.
- Prevent self-trading (a user's resting order shouldn't match their own new order).
- All order placement + matching must be a single atomic DB transaction (Prisma `$transaction`) — concurrent order submissions on the same market are the obvious race condition here, and this app already had to think carefully about concurrency once (`cache.ts`'s in-flight de-dupe for the exact same reason: cheap concurrent requests hitting a shared resource). Don't reintroduce that bug in the matching engine.
- Store every trade as an immutable row (for the price history chart) — don't just update a rolling "current price" field.

**Users, wallets, positions**
- Each user starts with a fixed virtual cash balance (make this configurable, e.g. an env var or seed constant — ask me what the default should be if I haven't said).
- Track open positions (contracts held, average cost basis) and realized/unrealized P&L.
- A portfolio page listing open positions and past settled trades.

**Settlement — must key off real data, never off Claude**
- A market resolves YES/NO the moment its underlying `Fixture.status === "FINISHED"` and `winnerTeamId` is known, exactly the same signal `road-to-final.ts` and Phase 2's pick scoring already use. Wire this into the existing refresh/cron path rather than building a second polling loop.
- Handle non-`FINISHED` terminal states explicitly: postponed/suspended/cancelled fixtures should **void** the market (full refund to all holders at the price they paid, not a $0/$1 settlement) rather than being silently left open or wrongly resolved.
- Handle the case where the scenario never becomes real at all — e.g. the tracked team is eliminated a round earlier, so a Quarter-Final scenario market never gets a fixture to resolve against. Void and refund these too. Decide and document the void condition precisely (e.g. "the round this market belongs to becomes `completed` in `RoundPath` without this scenario's opponent being the one who advanced").

**New Prisma models** (name however fits your conventions, but capture all of this):
- `Wallet` (balance, tied to the `User` model from Phase 2)
- `Market` (linked to a stage + scenario/opponent, status: open/settled-yes/settled-no/void, resolution source reference)
- `Order` (side, price, quantity, remaining quantity, status)
- `Trade` (immutable, price + quantity + timestamp, for the price chart)
- `Position` (per user per market: quantity, average cost)

Write the migration; don't hand-edit `dev.db`.

**UI** — reuse the existing visual language, don't import Kalshi's actual branding:
- Markets list/browse page
- Market detail: order book depth, a price-over-time chart (Trade history), buy YES/NO order ticket
- Portfolio/positions page
- The live last-traded price is where the `SplitFlap` component belongs — it's earned here, once there are active markets with frequent trades, not in Phase 1 or Phase 2. Look at `SplitFlap.tsx` before wiring it in.

**Phase 3 open design questions — answer in your plan or ask me:**
1. **Multi-outcome vs. independent binaries.** Within one round, the ranked scenarios are mutually exclusive — only one opponent will actually occur. Should scenario-markets in the same round be modeled as one linked multi-outcome event (Kalshi's "which of these" format, where exactly one leg resolves YES and it's structurally impossible for two to both resolve YES), or as fully independent binary markets that happen to usually sum near 100% but aren't enforced to? This changes the matching engine, the settlement logic, and the UI. Pick one and justify it, or ask me.
2. **Starting wallet balance** and whether users can ever go negative (e.g. is max loss capped at cost basis, which it should be for binary contracts bought outright — confirm you're not accidentally building margin/leverage).
3. **Order lifetime** — do resting orders expire (end of day, market settlement, never)?
4. **Durable storage for money-like data (see §0's `/tmp` warning).** Given this repo currently ships with SQLite-on-Vercel as a best-effort cache, propose how `Wallet`/`Order`/`Trade`/`Position` should be persisted for this feature to be real rather than best-effort. At minimum, flag this loudly in the README rather than silently shipping wallets that can lose money on a cold start. If you think a Postgres swap (Neon/Vercel Postgres/Turso, per the README's existing note about swapping `DATABASE_URL`) is in scope, say so and do it; if it's out of scope, document the limitation clearly.

**Testing & ADR conventions for this phase:**
- Matching engine: price-time priority, partial fills, self-trade prevention, atomicity under concurrent orders.
- Settlement: win, loss, void-on-postponed, void-on-scenario-never-materialized.
- Keep matching/settlement logic in pure, testable functions — not buried inside API route handlers — matching how `scenario-ranking.ts` is already structured.
- Write an ADR recording your answers to the four open questions above, plus the durability decision, so the reasoning is preserved in the repo, not just in chat history.

# ADR 0001 — Screenshot bracket ingestion

Status: accepted (Phase 1) · Date: 2026-07-10

## Context

Official APIs don't cover informal competitions that only publish a bracket
as an image. Phase 1 brings those into the same pipeline as
football-data.org: a `ScreenshotBracketProvider` implements `SportsProvider`
so caching, reasoning, ranking, and the UI need zero changes per data
source. The architectural rule is unchanged: **ground truth is never
generated by an LLM.** Claude vision only transcribes what an image shows,
its output is Zod-validated (`bracketExtractionSchema.ts`, forced tool call,
tool schema generated from the same Zod schema via `z.toJSONSchema` so the
two can't drift), and nothing becomes competition data until a human
confirms it.

## Supported formats & detection

Formats: `SINGLE_ELIM`, `DOUBLE_ELIM`, `ROUND_ROBIN`, `GROUPS_KNOCKOUT`.

Detection is automatic with a confidence threshold, embedded in the
mandatory confirmation step rather than a separate dialog: the extraction
returns `format` + `formatConfidence`; at or above
`CONFIDENCE_CONFIRM_THRESHOLD` (0.8, `src/lib/ingestion.ts`) the format is
pre-selected but editable, below it there is **no pre-selection** — the
rest of the preview stays disabled until the user picks a format. A guess
can never slip through because the human gate already exists for all data.

- **Double elimination**: rounds carry a `bracketSide`
  (WINNERS/LOSERS/MAIN); deterministic stage-key derivation
  (`draft-to-state.ts`) prefixes `WB_`/`LB_` and names the main round
  `GRAND_FINAL`. `road-to-final.ts` shows the *shortest remaining road*:
  losers-bracket rounds appear only once the team has actually dropped (or
  is scheduled there), winners-bracket rounds disappear once it has, and
  only a losers-bracket or grand-final loss ends the road
  (`EliminationRule` = `double-loss`). Grand-final bracket resets are out
  of scope.
- **Round robin**: ingests as standings (+ `GROUP_STAGE`); there are no
  knockout rounds for `/path` to show, so the value is the record/summary
  view. The record is derived from finished fixtures when standings are
  absent.
- **Group + knockout**: groups become `Standing[]`, knockout rounds become
  fixtures; goal difference is not extracted (rarely legible in
  screenshots) and defaults to 0.

## Per-field confidence & confirmation

Every extracted leaf is `{ value, confidence }`. In the preview
(`IngestReview.tsx`), fields under the threshold get an icon + text chip
("⚠ needs review"), never color alone (WCAG 1.4.1). Extraction output is
stored as a `DRAFT` `Ingestion` (source image + raw extraction + later the
user's corrections + the applied diff, together for debuggability); the
provider reads only confirmed `Competition` state, so a draft is
structurally invisible to the rest of the app.

The confirm endpoint re-validates the human-corrected payload with its own
Zod schema and converts it with pure deterministic code: stage keys, stable
slug team ids (existing teams keep their ids across re-ingestions), winner
resolution (explicit winner, else unequal scores; equal scores stay
`FINISHED` with no winner = inconclusive), ISO date normalization.

## Re-ingestion: diff-to-approve, never append-only, never silent overwrite

A later screenshot targets an existing competition. The proposal is diffed
against confirmed state (`state-diff.ts`): fixtures match by unordered team
pair within a stage, then positionally for TBD slots; additions are listed;
**contradictions** (changes to previously confirmed fields) are flagged
per-field with a "conflicts with confirmed data" chip and shown as
before → after in a live preview. Confirming applies exactly what was
shown; keeping an old value means editing the field back. Rationale:
append-only would make it impossible to fix a wrongly confirmed value or a
legitimately amended bracket, and silent overwrite would let bad OCR
*destroy* ground truth. The diff is persisted as `Ingestion.appliedDiff`.
Fixtures the new screenshot doesn't show are kept; stage order merges by
shared-stage anchors. Confirming also invalidates the competition's cached
Claude scenarios.

## Format vs. scoring system (forward compatibility)

`format` describes only the bracket shape (who plays whom). A separate
nullable `Competition.ratingSystem` column (null = win/loss elimination,
the only Phase 1 behavior) reserves the advancement axis: a future ELO-style
ladder is a new value there (e.g. `"ELO"`), an additive optional
`rating?: number` on `Standing`, and a skip of the elimination break — not
a schema migration. Deliberately not implemented in Phase 1.

## Security posture (Phase 1)

- Uploads validated by content: magic-byte sniffing (PNG/JPEG/WebP/GIF),
  5 MB cap, header-declared dimensions capped at 8000px without decoding
  (decompression bombs). Client MIME type is ignored.
- `/api/ingest` is a paid Claude call → fixed-window rate limits (per-IP
  and global) gate the extraction call specifically; the limiter is
  in-process, so on serverless it is per-instance (documented weakening).
- Mutating endpoints reject cross-origin browser requests via
  Origin/Sec-Fetch-Site checks. There are no cookies/sessions in Phase 1,
  so there is no ambient credential for classic CSRF; token-based CSRF
  arrives with sessions.
- Prompts fence untrusted data: screenshot text and screenshot-derived team
  names are declared data-not-instructions in both the extraction and
  scenario prompts. Rendering relies on React's default escaping; no
  `dangerouslySetInnerHTML`.
- **Known gap, do not carry silently into Phase 2:** ingestion, confirm,
  and competition selection are unauthenticated — anyone who can reach the
  deployment can confirm a draft or add competitions. This must be closed
  when Phase 2 introduces user accounts.

## Accessibility

Measured contrast on the ink background: chalk ≥50% opacity 4.81–16.8:1,
floodlight 16.1:1, live-red 4.78:1 — all pass AA for their text uses;
turf/50 borders are 1.63:1, fine as card decoration but insufficient as the
only boundary of a control, so form inputs use full-strength turf borders
(3.07:1) with floodlight focus. All controls are native and
keyboard-operable (no drag-only interactions; upload is a plain file
input); every field has a real `<label>`; async status and errors are
announced via `aria-live`/`role="alert"`; flags are icon + text. No new
animation was added (the split-flap stays reserved for Phase 3), and the
global `prefers-reduced-motion` rule still covers everything.

## Durability caveat

Unlike `CacheEntry`, `Competition`/`Ingestion` rows are **not
re-fetchable**. On Vercel's `/tmp` SQLite they vanish on cold start —
screenshot competitions require a persistent database (local dev, VPS, or a
hosted DB via `DATABASE_URL`). Documented in the README; the Postgres/Turso
swap was deliberately deferred (money-like data in Phase 3 forces the
decision anyway).
